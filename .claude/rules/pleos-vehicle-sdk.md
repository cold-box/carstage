# Pleos Vehicle SDK rules

- The dependency is `ai.pleos.playground:Vehicle:2.3.2` (the Pleos Nexus has only 2.0.3 and 2.3.2).
- One `VehicleSession` owns the `Vehicle` lifecycle: use it after `initialize()`, `release()` when the owner goes away.
- Wrap callback APIs with `awaitVehicle<T?>` / `awaitVehicle2<A?, B?>` / `awaitVehicle3<A?, B?, C?>`. Keep the type arguments nullable (callbacks are contravariant, so this fits whatever nullability the SDK declares). A callback that never comes throws `VehicleCallTimeoutException` after 5 s.
- Before writing, always check the area (`SeatArea`) and range with `check...Capabilities`. Never hard-code areas: they differ by car model.
- A write's success callback means "request handled", not "value changed". Re-read or listen when it matters.
- Unregister a listener with the same instance and area used to register it.
- Declare only the permissions you use. They are all `protectionLevel="normal"`, so there is no runtime request.
    - The gear (`Gear`) needs `pleos.car.permission.CAR_DRIVE`. `CAR_POWERTRAIN` is not defined on the device.
    - `PRIVATE_*` permissions are not available to third-party apps.
- The `Brake` API only has the brake pedal state. Parking is decided from `Gear`'s `GEAR_PARK`.
    - SDK 2.3.2 marks `getCurrentGearSelectionState` deprecated in favor of Android's standard `GEAR_SELECTION` property (`CarPropertyManager`), a compile warning. The safety rules (`safety/VehicleDriveReader`) keep the SDK call on purpose: gear changes read immediately on the emulator, and the standard property would add another permission and connection path. Move to the standard property if this call fails on a real car or a newer SDK.
    - A gear read with no answer within 1 s is "unknown". One unknown pauses commands; two in a row close the stage.
- Defroster and wipers are read per area (`WindowArea`) from their capabilities. An empty or null area list is "unknown" and is not cached. Any wiper value other than `OFF` counts as running. Unknown blocks climate effects.
- The release build does not drive the cabin (`releaseDrivesCabin` in `app/build.gradle.kts`). Its manifest removes `CONTROL_CAR_*` and `CAR_LIGHTS`, which only control used (`src/noCabinControl/AndroidManifest.xml`), and the car output `VehicleCabin` (`src/cabinControl`) is left out entirely. `AppGraph` gets the car output from `carCabin()`, which is `null` in builds without control, so the stage drives only the simulator. In the release APK's dex, car write calls remain only in the Pleos SDK's own interface classes, none in our code. Unit tests touching `VehicleCabin` live in `src/testDebug`. Pleos rejects apps that declare unapproved permissions or call their APIs. Debug builds always drive the cabin (regression tests and effect checks).
- Without the control permissions (`CONTROL_CAR_LIGHTS`, `CONTROL_CAR_CLIMATE`, `CONTROL_CAR_SEATS`), reads and capability queries still work (they even answer `access=READ_WRITE`), and only writes are refused within 1 ms with `SecurityException("set… need Permission")` (`docs/05` "차량 제어 권한이 없을 때"). Detect it with `isControlDenied()` (a `SecurityException` in the cause chain). `ControlDenials` remembers refused targets for the stage and does not resend them; the next stage retries once (a real car may refuse for reasons other than permission). To test, temporarily remove the three lines from the manifest and build with `assembleDebug` (lint fails with `MissingPermission`, so restore them before committing).
- Effect writes go through `stage/VehicleCabin`. Areas and ranges come from capability queries; the driver is the area holding only `SeatValue.ROW_1_LEFT`, the passenger only `ROW_1_RIGHT`. The app never turns the climate power on.
    - If a capability query fails (timeout, service error), do not settle on "unsupported"; query again at the next effect. Only an answer of "no area" means unsupported.
    - Restore with the original value exactly as the SDK returned it. The ambient switch also has `AUTOMATIC`, so restoring through a Boolean is wrong.
    - The product's `VehicleCabin` writes the original value to `RestoreJournal` (app `files/stage/`) right before first changing a target, and refuses the write if it cannot. When the stage ends (`ended`) it clears the journal except targets whose restore failed. `StageRecovery` restores leftovers with `restoreOriginals`, and no new stage opens before that. If the car cannot be reached or a journaled target's capability query fails, the journal stays for the next try. Other per-target write failures (except the driving refusal below) are reported and cleared, since keeping them would retry and warn at every start and open.
    - Restore writes are always sent: neither the acknowledgement nor a re-read guarantees the real value (the emulator sometimes acknowledges a reading-light write while the read value stays). If refused because the car is driving (`isDrivingRestricted`), the remaining clue is a re-read (1 s limit): the original value means restored, anything else is deferred (`VehicleCabin.restoreOne`, `CabinRestoreDeferred`). Deferred targets stay journaled, and `ParkedRestore` reads the gear every 2 s and restores once parked. Targets whose restore failed at close get one more try the same way. A `VehicleCabin` without a journal (Lab probes) treats a deferred restore as a failure.
    - Journal recovery (`StageRecovery.run`) reads the gear after its writes; if parked by then, a driving-refused restore is cleared as a failure. Opening a stage reads the gear first, restores, then reads again, so a new stage never takes a value still to be restored as its original.
    - Restores run only while the stage is closed (`StageController.whileClosed`). Never treat an open stage's journal as the "last stage" and restore it.
    - A new `CabinTarget` also goes into `RestoreJournal.keyOf`/`targetOf` and `VehicleCabin.writeRaw`. Originals are written as text: enum names, numbers as numbers (`VehicleCabin.encode`).
- Fan speed is sent as a step offset (`CabinCommand.FanStep`). On the first offset `VehicleCabin` reads the value just before as its base (the stage-start value if unreadable), adds the offset clamped to the range (never crossing the base the other way), and returns to that base at offset 0. Returning is also a climate effect, so it waits while the defroster or wipers run (the mixer keeps asking). Manual fan speed turns climate AUTO off in many cars, and the app neither reads nor restores AUTO; check on a real car (on the emulator `auto_on` stays). The emulator reflects fan writes in Virtual Console (`fan_speed`) while climate power is on.
- Temperature uses `checkHvacTemperatureCapabilities` (SDK 2.3.2 recommends the overload returning three values, so `awaitVehicle3`), `getHvacTemperature` and `setHvacTemperature`, always with `TemperatureUnit.CELSIUS`. Areas: driver `ROW_1_LEFT` (areaId 1), passenger `ROW_1_RIGHT` (areaId 4); the emulator range is 15.0–30.0 °C in 0.5° steps. Effects send offsets (`CabinCommand.Temperature`), which `VehicleCabin` turns into set points like the fan (base = value just before). With dual climate off, changing one side may move the other, and a car with climate power off may switch climate or dual on when given a set point; check on a real car (the emulator only acknowledges, whatever the climate power). A temperature someone changes by hand while the stage is open is where the announcement returns to; closing the stage restores the stage-start value (restore writes are always sent).
- Seat occupancy: find the front-seat areas (each holding only `ROW_1_LEFT` or `ROW_1_RIGHT`) with `checkSeatOccupancyCapabilities` and read with `getCurrentSeatOccupancy` (`vehicle/SeatOccupancyReader`, permission `CAR_SEATS`). Remember the areas only when both seats are found; otherwise query again at the next read. An unread seat is unknown, and unknown never suggests a duel. Reading `true` as "occupied" is an assumption from the function name: the official docs do not define `true`, and on emulator v2.1.0 the SDK value is the opposite of Virtual Console and the standard `SEAT_OCCUPANCY` (`docs/05` "착석 감지 확인"). Confirm the meaning with Pleos before relying on it on a real car.
- EV battery: `vehicle.getEvBattery()`'s `getEvBatteryStateOfCharge` (percent, `Int?`) and `getEvChargeSwitchState` (charging, `Boolean?`), permission `pleos.car.permission.CAR_ENERGY`. The charge switch is READ_WRITE, but the app never controls charging. The product reads through `vehicle/EvBatteryReader`. Support is remembered only after both capability queries (`checkEvBatteryStateOfChargeCapabilities`, `checkEvChargeSwitchCapabilities`) answer; both answering with no config (null) means a car without an EV battery; if only one answers, only that value is read; a failed query asks again at the next read. An unread charge switch is unknown, and the last-song question (`ChargeFinish`) never takes unknown as charging finished.
- Trip: `vehicle.getOdometer()`'s `getTripCurrentDrivingTime` (`Int?`) and `getTripCurrentDrivingDistance` (`Float?`) (`vehicle/TripReader`, for the MC's greeting). The total distance (`getCurrentDistanceDriven`) read with the permissions already declared (`CAR_DRIVE` for driving); whether trip reads need anything more is unverified because the emulator does not support them. Units are undocumented: assumed minutes and km, trusted only at ≤ 12 h and an average speed above 3 and at most 200 km/h (`Trip.believableMinutes`). Emulator v2.1.0 refuses all six trip values (current, cumulative and since-refuel time and distance) from the capability query on with `ERROR_NOT_SUPPORTED_PROPERTY`. Queries go through `awaitSupported`, which treats no config (null) and that answer (`isNotSupported()`) as unsupported; support is remembered only after both queries answer, and any other failure asks both again at the next read. Test on the emulator with the debug build's `--es trip <minutes>` (`docs/05` "주행 기록(Odometer) 확인").
- Car kind (EV, plug-in hybrid, combustion) comes from Android's standard `CarPropertyManager` `INFO_FUEL_TYPE`, not the Pleos SDK (`vehicle/CarKind`). The permission `android.car.permission.CAR_INFO` is normal, granted at install. Fuel-only cars never read `EvBattery`; when the car does not report its fuel type, the `EvBattery` capability query decides.
- Night comes from Android's standard `NIGHT_MODE` via `CarPropertyManager.registerCallback` (ON_CHANGE; registering delivers the current value first), not the Pleos SDK (`vehicle/NightModeReader`). The permission `android.car.permission.CAR_EXTERIOR_ENVIRONMENT` is normal. The headlight state (`HEADLIGHTS_STATE`) needs `CAR_EXTERIOR_LIGHTS`, which is signature|privileged, so it cannot be read. The recommended `subscribePropertyEvents` and `CarPropertyValue.getPropertyStatus` exist only from API 35, so they are not used (minSdk 28; the emulator is Android 14, API 34). A car service restart or an error callback keeps the last value; on reconnect the subscription is rebuilt and the current value arrives. If the car says it cannot give a value (status not `STATUS_AVAILABLE`), it is unknown (day). The emulator's value is off and Virtual Console cannot change it, so test with the debug build's `--es night on|off|car` (`docs/05` "야간 밝기 배려 확인").
- Check API signatures in the official docs (the Vehicle API reference on document.pleos.ai). The pages render with scripts, so read them in a browser or let Gradle's build errors tell you the right type.

# Pleos emulator (v2.1.0) behavior

- Ambient light has a single area covering every seat (`ROW_1_LEFT+ROW_1_RIGHT+ROW_2_*`). Left/right separation comes from reading lights, temperature (`ROW_1_LEFT`/`ROW_1_RIGHT`) and seat ventilation.
- Writes that actually change the value: ambient switch, seat ventilation.
- In gear D, reading-light writes are refused with `Exception` (message `java.lang.IllegalArgumentException: 50001`) within 1–4 ms (R and N not checked). Ambient brightness and color writes are not refused in D. Treat it as the SDK docs' `ErrorCode.ERROR_DRIVING_RESTRICTED`; it arrives as a bare numeric exception rather than a `VehicleException`, so `isDrivingRestricted()` recognizes both.
- In gear P, these writes are acknowledged but do not change the value: ambient color and brightness, reading lights, climate power. (With Virtual Console connected, reading-light writes did show in its `reading_lights`, and ambient color and brightness appeared to change; the console's ambient `mode` is separate from the SDK switch value.) With climate power off, fan writes fail with `PropertyAsyncError error code 2` (NOT_AVAILABLE).
- Ambient color values look like `0x00RRGGBB` (initially `0x00FFFFFF`).
- Write responses take 1–25 ms, and changing every 150 ms does not fail (whether the value is applied is a separate matter).
- Gear, charge switch and charge level changed in Virtual Console (`scripts/vconsole.sh`) read in the app immediately. Test code that reacts to gear or charging by changing state with that script.
