# 차량 제어가 막힐 때의 기획 (Plan B)

- 작성일: 2026-10-24
- 결정: 2026-10-31에 시나리오 D로 정했습니다(9장).
- 목적: Pleos가 서드파티 앱의 차량 제어(조명, 공조, 시트)를 허용하지 않을 때에도 앱이 제 역할을 하도록, 시나리오별로 제품 설명과 화면·소리 연출을 미리 정해 둡니다.
- 관련 문서: 화면 설계 [10](10-ui-ux-plan.md), 에뮬레이터 확인 [05](05-emulator-findings.md) "차량 제어 권한이 없을 때"

## 1. 왜 필요한가

- Pleos Playground 문서에서 신청 없이 쓸 수 있는 SDK는 Vehicle State(읽기)와 NaviHelper뿐이고, Vehicle Control은 "Coming Soon"입니다([프로젝트 생성](https://document.pleos.ai/docs/pleos-only/create-my-project)). Vehicle 권한은 Pleos App Market과 사전 협의와 승인을 거쳐야 선언할 수 있습니다([Vehicle 권한](https://document.pleos.ai/docs/pleos-only/connect-sdk-pleos/)).
- 그래서 공모전 심사나 실차 배포 시점에 조명·공조·시트 제어를 쓸 수 있을지 미리 알 수 없습니다. Pleos의 답이 "안 된다"이거나 "아직 모른다"일 수 있습니다.
- 에뮬레이터에서 제어 권한을 빼 보니, 읽기와 capability 조회는 그대로 되고 쓰기만 모두 1ms 안에 `SecurityException`으로 거절되었습니다(2026-10-24, [05](05-emulator-findings.md)).
- 앱은 이미 이 상황에서 스스로 버팁니다.
  - 거절된 기능은 그 무대 동안 다시 보내지 않고, 다음 무대에서 한 번 다시 시도합니다.
  - 허용된 기능, 실내 시뮬레이터, 효과음은 그대로 반응합니다.
  - 무대마다 처음 거절될 때 "차가 허용하지 않은 기능은 화면에서만 반응해요."를 보여 주고, 무대를 닫으면 내립니다.
- 남은 일은 코드가 아니라 기획입니다. 제어가 없을 때 "무엇이 이 앱의 가치인지", "화면과 소리를 어떻게 키울지"를 미리 정해 둡니다.

## 2. 시나리오

| 시나리오 | Pleos 답의 예 | 사용자가 겪는 것 | 앱이 스스로 하는 것 | 우리가 준비할 것 |
|---|---|---|---|---|
| A. 제어 전부 허용 | "Vehicle 권한을 신청하면 쓸 수 있다" | 노래에 맞춰 실내 조명, 독서등, 바람, 시트 통풍이 반응합니다 | 지금 설계대로 전체 연출을 합니다 | 권한 신청과 협의 절차를 일정에 넣습니다. 무대 글로우는 화면 연출로 그대로 씁니다 |
| B. 일부만 허용 | "조명은 되지만 공조·시트는 안 된다" | 허용된 기능(예: 조명)만 차에서 반응하고, 나머지는 화면에서만 보입니다. 처음 거절될 때 안내가 한 번 나옵니다 | 거절된 기능만 빼고 나머지는 그대로 보냅니다 | 빠진 기능의 연출을 화면과 소리로 메웁니다(예: 시트 통풍 축하 대신 화면 좌우 빛과 효과음) |
| C. 제어 불가, 읽기만 가능 | "공모전 기간과 출시 때 모두 제어는 안 된다" | 차 실내는 바뀌지 않습니다. 화면 전체 글로우, 효과음, 점수, 대결이 무대가 됩니다. 정차·충전·착석·통화에 맞춰 시작하고 멈추는 동작은 그대로입니다 | 모든 쓰기가 거절되고 안내가 나옵니다. 읽기 기반 기능은 모두 동작합니다 | 제품 설명을 4장의 Plan B로 바꾸고, 화면과 소리 연출을 주인공으로 키웁니다(5장) |
| D. 심사 때는 불가, 출시 후 열림 | "Control SDK는 추후 공개 예정이다" | 심사·시연 때는 C와 같고, 제어가 열리고 권한 협의를 마치면 코드를 고치지 않고 A처럼 반응합니다 | 무대마다 제어를 다시 시도하므로, 권한이 생기면 바로 차가 반응합니다 | 단계별 동작(C에서 A로)을 정해 두고, 출시 때의 권한 협의 계획을 세웁니다 |

Pleos의 답을 확인하지 못하면 D로 보고 준비합니다. D는 C의 준비를 모두 포함하므로, 어느 답이 나와도 손해가 가장 적습니다.

## 3. 제어 없이도 남는 것

| 구분 | 기능 | 쓰는 차량 정보 | 제어가 없을 때 |
|---|---|---|---|
| 읽기만 씀 | 정차 판단과 주행 시 일시 중지 | 기어, Android 주행 규제 상태 | 그대로 동작합니다 |
| 읽기만 씀 | 공조 연출 생략 조건 | 성에 제거, 와이퍼 | 공조 연출이 없으므로 의미가 줄지만 동작은 그대로입니다 |
| 읽기만 씀 | 2인 대결 제안 | 앞좌석 착석 | 그대로 동작합니다 |
| 읽기만 씀 | 충전 표시, 충전이 끝나면 마지막 곡으로 마무리, 잔량이 낮으면 공조·시트 연출 빼기 | 전기차 배터리, 충전 스위치 | 그대로 동작합니다(잔량 보호는 제어가 없으면 할 일이 없음) |
| 읽기만 씀 | 차 종류별 공회전 경고 | Android 표준 연료 종류 | 그대로 동작합니다 |
| 차와 무관 | 통화 중 자동 멈춤, 음악 재생 감지 실행 제안 | Android 오디오 상태 | 그대로 동작합니다 |
| 차와 무관 | Gleo 음성 실행("노래 무대 열어줘") | Gleo App Schema | 그대로 동작합니다 |
| 차와 무관 | 흥 점수, 곡 종료 감지, 2인 대결 진행과 결과 | 마이크 분석 | 그대로 동작합니다 |
| 차와 무관 | 효과음(짧은 박수, 박수, 팡파레와 박수, 드럼롤, 팡파레) | 오디오 포커스 | 그대로 동작합니다 |
| 차와 무관 | 실내 시뮬레이터, 무대 글로우(진행 중) | 앱이 정한 연출 값 | 그대로 동작합니다. 차 대신 반응을 보여 주는 주인공이 됩니다 |
| 제어가 필요 | 앰비언트 조명 색·밝기(참여, 곡 분위기, 환호 출렁임) | Light 쓰기 | 화면 글로우로 대신합니다 |
| 제어가 필요 | 독서등 반짝임(환호), 대결 차례 표시 | Light 쓰기 | 화면의 좌우 빛과 대결 색으로 대신합니다 |
| 제어가 필요 | 시트 통풍과 온도(대결 승자 축하) | Seat·HVAC 쓰기 | 화면 승자 쪽 빛과 팡파레로 대신합니다 |
| 제어가 필요 | 풍량(피날레 환호 바람, 10/25 구현) | HVAC 쓰기 | 효과음과 화면 출렁임으로 대신합니다 |
| 제어가 필요 | 피날레와 대결 발표의 차량 연출 | 위의 쓰기 전부 | 같은 시간표를 화면과 소리로 냅니다 |

정리하면, 제어가 없어도 "언제 시작하고 멈추는가"(상황 인식)와 "사람에게 반응하는가"(목소리·환호 분석, 점수, 대결)는 모두 남습니다. 빠지는 것은 "차 실내가 직접 바뀌는 출력"뿐입니다.

## 4. Plan B 제품 정의

- 지금 한 줄 소개: "탑승자의 목소리와 환호에 차가 반응한다."
- Plan B 한 줄 소개(안): "탑승자의 목소리와 환호에 차 안의 큰 화면과 스피커가 반응하고, 차의 상태에 맞춰 무대가 스스로 열리고 멈춥니다."
- 차별점은 그대로 둡니다. 기아 사운드 무드 램프 같은 기존 기능은 재생 음악에 반응하고, 노래방 앱의 채점은 화면에만 나옵니다. CarStage는 "사람의 목소리와 환호"에 반응한다는 점이 다릅니다([기아 사운드 무드 램프 매뉴얼](https://ownersmanual.kia.com/ivi/DA_GEN2_V/AV/KOR/Korean/002_Features_soundmoodlamp.html)).
- 차량특화성은 출력이 아니라 상황 인식으로 설명합니다. 휴대폰 노래방 앱과 비교하면 다음이 남습니다.

| 비교 | 휴대폰 노래방 앱 | CarStage (제어 없음) |
|---|---|---|
| 반응하는 것 | 손 안의 화면 | 차 전면의 큰 화면과 차 스피커, 탑승자 모두가 같은 무대를 봅니다 |
| 상황 인식 | 없음 | 기어, 충전, 착석, 통화, 다른 앱의 음악 재생에 맞춰 시작하고 멈춥니다 |
| 인원 인식 | 직접 입력 | 앞좌석 착석으로 2인 대결을 제안합니다 |
| 실행 | 앱을 찾아 누름 | Gleo 음성, 음악이 나올 때 첫 화면 제안 |
| 안전 | 해당 없음 | 운전이 시작되면 무대를 멈추고 화면 연출을 숨깁니다 |
| 확장 | 없음 | 차량 제어가 열리면 같은 무대가 조명·공조·시트로 넓어집니다(코드는 그대로, 권한 협의만 필요) |

- 지키는 원칙은 바뀌지 않습니다. 음원·가사·반주를 제공하지 않고, 오디오를 저장하거나 보내지 않으며, 정차 중에만 동작합니다. 외부 조명은 어떤 경우에도 건드리지 않고, 화면 연출을 키우더라도 알림(특히 헤드업 알림)으로 대신하지 않습니다.

## 5. 화면과 소리로 대신할 것

### 무대 글로우 (진행 중, [10](10-ui-ux-plan.md) 8장 PR 3)

- 무대가 열리면 화면 가장자리부터 지금 연출 색의 빛이 깔리고, 목소리가 반주보다 커지면 밝아집니다. 연출 엔진이 차와 시뮬레이터에 보내는 같은 값을 따라가므로, 제어가 있든 없든 화면은 똑같이 반응합니다.
- 곡 분위기에 따라 바탕 빛이 숨 쉬듯 오르내리고, 환호에는 짧게 출렁입니다. 피날레에서는 등급 색(기본 따뜻한 흰색, 좋음 보라, 최고 금색)으로 바뀝니다.
- 대결에서는 화면 가장자리 전체가 차례인 사람의 색(운전석 파랑, 조수석 빨강)으로 빛납니다. 발표 때는 좌우가 따로 움직입니다. 독서등이 켜진 쪽 가장자리가 그쪽 색으로 분명히 빛나고 반대쪽과 위아래는 어두워져, 빛이 독서등과 함께 화면을 가로지릅니다. 마무리에서는 승자 쪽 가장자리가 남고, 무승부는 왼쪽 파랑과 오른쪽 빨강으로 화면이 나뉩니다(10/25 구현, [05](05-emulator-findings.md) "대결 발표의 화면 좌우 빛 확인"). 드럼롤과 팡파레도 같은 쪽으로 옮겨 가므로, 차의 독서등이 하던 "좌우" 표현을 화면과 소리가 함께 맡습니다.
- 빛은 0.5초 이상에 걸쳐 바뀌고 깜빡이지 않습니다. 주행이 시작되면 숨깁니다([10](10-ui-ux-plan.md) 5장 "움직임").

### 소리

- CC0 효과음은 그대로 씁니다. 등급별 피날레(짧은 박수, 박수, 팡파레와 박수)와 대결 발표(드럼롤, 팡파레)입니다.
- 드럼롤을 좌우 스피커로 번갈아 보내는 작업을 앞당깁니다. 독서등이 하던 좌우 번갈이를 소리로 옮기는 것이라, 제어가 없을 때 가장 효과가 큽니다.
- MC 멘트는 Pleos TTS가 "Coming Soon"이라, 기본 Android TTS 엔진이 있으면 쓰고 없으면 미리 녹음한 짧은 멘트로 대신합니다. 효과음과 같은 오디오 포커스 규칙을 따릅니다. 2026-10-31: Pleos TextToSpeech SDK의 `ON_DEVICE` 모드로 바꿔 에뮬레이터에서도 말합니다. 차량 제어가 없을 때 차가 말로 무대를 이끄는 역할이 커져서, 무대 인사, 곡 점수, 대결 차례, 충전 완료까지 말하는 "차를 아는 MC"를 넣었습니다([12](12-mc-plan.md)).

### 실내 시뮬레이터

- A에서는 "앱이 차에 보낸 명령"을 그대로 보여 주는 화면이고, 에뮬레이터가 조명 값을 바꾸지 않는 문제를 메웁니다.
- C·D의 실차에서는 차 실내가 바뀌지 않는데 그림만 바뀌면 사용자가 헷갈릴 수 있습니다. 그래서 C로 정해지면 시뮬레이터를 "차가 제어를 허용하면 이렇게 반응합니다"라는 미리보기로 보여 주고, 무대의 주인공은 화면 전체 글로우로 옮깁니다. 이 표현은 C로 정해진 뒤 [10](10-ui-ux-plan.md) 6장의 시뮬레이터 그림 작업에서 함께 바꿉니다. 2026-10-31에 구현했습니다. 앱이 켜진 뒤 차가 제어를 거절한 적이 있으면 그림 위에 "미리보기 · 차가 허용하면 실내가 이렇게 반응해요"를 두고, 레이아웃은 바꾸지 않았습니다(무대의 빛은 이미 화면 글로우가 맡음, [10](10-ui-ux-plan.md) 6장, [05](05-emulator-findings.md) "실내 그림의 미리보기 표시 확인").

## 6. 출시 빌드와 개발 빌드

2026-11-02부터 제출하는 출시 빌드는 제어를 끈 판입니다(빌드 스위치 `releaseDrivesCabin`). 이 판에서는 실내 그림 위의 미리보기 줄과 함께 화면만 반응하고, 제어를 켠 개발 빌드에서는 같은 노래에 차량 쓰기가 나갑니다. 차량 출력 코드(`VehicleCabin`)를 넣느냐만 다르고 나머지 코드는 같습니다(9장). (2026-10-31에는 권한을 뺀 빌드를 따로 만들고 제출하지 않을 계획이었습니다.)

## 9. 결정 (2026-10-31)

시나리오 D(심사 때는 제어 불가, 출시 후 열릴 수 있음)로 준비합니다. D는 C의 준비를 모두 포함하므로, 나중에 다른 답이 나와도 버리는 작업이 없습니다.

### 근거

- 공모전 [FAQ](https://appdevchallenge.auto-hmg.io/faq)는 쓸 수 있는 SDK로 Vehicle SDK를 꼽지만, "각 SDK의 현재 제공 상태와 사용 조건은 SDK 문서 페이지에서 확인해 주세요"라고만 답합니다. 그 SDK 문서에서는 Vehicle Control이 여전히 "Coming Soon"이고, Vehicle 권한은 App Market과 사전 협의를 거쳐야 선언할 수 있습니다(1장).
- 공모전 [개발 환경 안내](https://appdevchallenge.auto-hmg.io/guide/development)의 예시 앱 세 개(주행 습관 점수, 음성 메모, 배달 동선)는 모두 차량 상태 읽기, NaviHelper, 음성만 씁니다. 차량 제어를 쓰는 예시는 없습니다.
- 10/31에 공모전 사이트의 FAQ와 [공지사항](https://appdevchallenge.auto-hmg.io/notice)을 확인했지만, 차량 제어를 쓸 수 있다는 안내는 찾지 못했습니다. 7장의 기준대로 답이 없으면 D로 봅니다.

### 바로잡은 표현

- 처음에는 "제어가 열리면 업데이트 없이 반응한다"고 썼습니다. 이 말은 출시 APK에 제어 권한(`CONTROL_CAR_*`)을 선언한 채로 App Market 심사를 통과해야만 맞습니다. 권한은 사전 협의 뒤에 선언해야 하므로, 출시 때 권한을 빼야 한다면 나중에 권한을 다시 넣는 업데이트가 필요합니다.
- 그래서 "코드를 고치지 않고, 권한 협의만 마치면 차 실내까지 반응한다"고 씁니다. 2장과 4장의 문구를 이 기준으로 고쳤습니다.

### 출시 빌드의 제어 권한 (2026-11-02 정함)

- (2026-10-31) 처음에는 제출 APK에 제어 권한을 계속 선언할지 정하지 않고(7장 두 번째 줄), 확인할 때까지 선언해 두기로 했습니다. 2026-11-02에 아래처럼 바꿨습니다.
- 2026-11-02: Pleos 문서([Pleos Connect SDK](https://document.pleos.ai/en/docs/pleos-only/connect-sdk-pleos/))는 "Declaring an unapproved permission or calling the corresponding API causes the app to fail app review."라고 적습니다. 권한만 빼도 앱이 제어 API를 부르면 걸리므로, 출시 빌드는 제어 권한을 선언하지 않고, 제어 API를 부르는 코드(`VehicleCabin`)도 넣지 않게 했습니다(빌드 스위치 `releaseDrivesCabin = false`). 출시 빌드의 무대는 차량 출력 없이 시뮬레이터만 움직이고, 실내 그림은 처음부터 미리보기로 표시합니다. 개발 빌드는 그대로 차를 제어해 에뮬레이터 시험에 씁니다([05](05-emulator-findings.md) "출시 빌드의 차량 제어 끔 확인").
- (2026-10-31) 제출 APK가 권한을 선언하면, 에뮬레이터에서 돌릴 때 차량 쓰기가 실제로 나갑니다. 2026-11-02부터는 제출하는 출시 빌드가 제어를 하지 않으므로 이 일은 없습니다.
